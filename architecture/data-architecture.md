# Data Architecture

> Status: Proposed baseline 2.0 · 16 October 2026 · DEC-04/06/10/12

Neon-managed PostgreSQL hosts four **logical databases**, each with an owner login, a restricted application login, and a separate migration login used only by that service's one-shot migration task. Neon is external to local Compose and Kubernetes workloads; applications connect over TLS using per-service connection strings. Applications cannot connect to another owner's DB. Administrators provision database roles; application logins have no schema DDL or cluster administration rights.

## Transaction and idempotency constraints

Booking uses a unique `(principal_id, operation, idempotency_key)` index and a canonical JSON request fingerprint. Atomic insertion reserves the key in the **same transaction** as parcel, price snapshot, quote consumption, history and outbox. Concurrent duplicates wait for the winner then return its stored status/body; same key with a changed fingerprint returns `409`. After an unresolved lock/deadline return `409 operation_in_progress` with Retry-After; retry using the same key. A committed response remains reproducible for 30 days; expired keys return `409 key_expired` rather than silently creating another parcel. Quotes are single-use; repeated keys are resolved before checking quote expiry/consumption. Merchant external-order uniqueness is retained for the order's lifetime, independent of API key rotation.

Status updates compare `expectedVersion` in an atomic conditional write. Update parcel, assignment if needed, history and outbox together. No notification or webhook occurs inside that transaction. Consumer inbox/job creation commits before broker ACK. Outbox relay marks published only after broker confirmation and may publish a duplicate after crash. See [state rules](parcel-state-machine.md).

## Customer booking storage and tariff zone

On 23 October 2026 the user selected **`deliveryAddress.zoneId`** as the tariff zone. Resolve the tier by that zone, package size and pricing version; `parcels.zone_id` and `price_snapshots.zone_id` retain the same delivery zone. Validate `pickupAddress.zoneId` independently as an eligible active service zone, and preserve it with the pickup address; it does not select the tariff. No pickup/delivery zone-pair price or cross-zone surcharge is defined.

Persist the complete validated QuoteInput in `quotes.delivery_input` JSONB, including both structured addresses, recipient name/phone and package weight/size. Bind its canonical fingerprint to the authenticated owner and retained `pricing_tier_id`, `pricing_version` and `currency`. At confirmation, reconstruct details from that persisted input; do not accept replacement address/contact/owner fields. Each address is serialized as structured JSON into the existing parcel text column (`pickup_address` / `dropoff_address`), retaining street, city, postalCode and zoneId. `dropoff_contact` retains the recipient name and phoneNumber as structured JSON text. `pickup_contact` is nullable: QuoteInput has no sender/pickup contact field, and no new required input is introduced. Phase 1 provides storage primitives; later application handlers enforce this mapping and zone selection.

Phase 1 stores unique tracking numbers, retained tier/version/currency references, ten-minute quote expiry, single-use owner-bound quote consumption, and an immutable accepted snapshot. Money uses numeric(18,2), LKR and half-up rounding; positive weight up to 30 kg uses numeric without an added decimal-place limit. Snapshot foreign keys retain both tariff provenance and the parcel's delivery zone. Quote/tariff optimistic concurrency uses PostgreSQL xmin; parcel version is a separate application concurrency token. Tariff economic fields are immutable in Phase 1: create a new row/version to change a price; activation may change.

`idempotency_keys.stored_response` is a JSONB envelope `{statusCode, body, location}`. The body is a string containing the exact serialized response; `expires_at` is 720 UTC hours after creation. The completed envelope and expired-key tombstone remain immutable. Resolve an identical committed result before quote expiry/consumption checks; replay its original status, body and Location. An expired retained key returns `409 key_expired`. The outbox payload retains parcel/version provenance in the StatusChanged v1 JSON; it is not a SQL foreign key or evidence of broker delivery.

## Courier operations and private notes

Delivery owns explicit couriers operational profiles and courier_zones memberships; the local couriers.id equals the referenced Identity user ID, without a cross-database foreign key. assignments.courier_id is a local FK to couriers.id, and courier_zones has a unique (courier_id,zone_id) pair. Seed only verified Courier identities for the demo. Store service_date on each assignment and evaluate daily/overdue queries in configured Operations:TimeZone (proposed Asia/Colombo). Active/on-duty/capacity/zone checks run atomically with assignment.

booking_history.delivery_note stores the required private note for PickedUp/InTransit/OutForDelivery; Failed stores its reason, and proof_metadata.recipient_name belongs to the final proof record. Public summaries and broker events must not serialize these fields.

## Proof and receipt storage

Delivery alone has a private bucket credential. Upload accepts JPEG/PNG by decoded content, at most 5 MiB for each photo/signature (10 MiB combined), with generated object keys; reject executable or malformed data. Stage the upload, confirm object persistence, then authorize and commit proof metadata, `Delivered`, history and outbox with the expected version. A storage failure leaves state unchanged; a transaction failure leaves only an orphan staged object. A daily cleanup removes unreferenced objects older than 24 hours; committed references are protected. Retrying uses the original idempotency key and fingerprint.

Download proof/receipt only via authenticated Delivery endpoints after ownership checks, returning streamed bytes with private/no-store headers. No permanent public URLs or proof identifiers appear in anonymous tracking. Receipts are generated from the immutable snapshot for Delivered parcels. Courier proof upload does not grant receipt access.

## Migrations and retention

Neon databases and owner roles must be provisioned before API startup. Each future image must run a single explicit migration task before readiness; production-style multi-replica automatic migrations are not promised. Verify notification migrations as well as the three APIs. Retain demonstration parcel/history records until an approved deletion policy exists. Purge expired refresh sessions, notification/provider and webhook attempt records after 30 days; never delete unresolved jobs or idempotency tombstones required for deduplication. Logs contain IDs/codes, not credentials or contact/address payloads. Backups, restore verification and retention acceptance remain implementation tasks.

Keep the Delivery eventId→parcel/version provenance index (outbox/history reference) for at least the 30-day consumer replay horizon and for all unresolved notification jobs. NotificationContext must remain able to validate an old but pending event after a broker outage; an outbox cleanup must not make durable jobs unresolvable. Merchant dashboard projections store authoritative Delivery terminal timestamps, never the local polling time.
